# PVF 大文件卡死排障与「页式 TXT 秒开」方案

> 记录 2026-09-30 对 `list/equipment.lst`（2740 万字符 / 41.4 万行）卡死的完整排障过程。
> 结论适用于**任何"文本过大"的文件**（`list/*.lst`、巨表、超大 `.etc`），不是某个文件的个案。

---

## 一、现象

- 工具内打开 `list/equipment.lst`：界面停摆 **43 秒**，恢复后**每 11 秒一轮**继续停摆。
- 同一文件「导出 → 系统记事本打开」：**秒开**。
- 后端日志显示读取只要 **265 ms**，`GetFile` IPC 也只有 568 ms。

---

## 二、排障：先打点，再对照（关键方法）

### 1. 前端打点（`markTrace`，进操作时间线，卡死时可空控制台敲 `SCRZ` 打出来）

在 `CodeEditor.vue` 的 `onMounted` 里分别记录：建状态（文档+扩展）、建视图（`new EditorView`）、
填文本、首帧，以及**详情**（渲染行数 / 文档行数 / 滚动区高 / 宿主高）。

实测（V4.5.5 一次）：

```
GetFile 返回      27,406,042 字符
编辑器建状态      28 ms
编辑器建视图      24,366 ms   ← 真凶
编辑器首帧        31,865 ms
```

### 2. 再对照：把变量逐个排除

| 对照实验 | 结果 |
| --- | --- |
| 后端解码 4.13MB → 27.4MB | 265 ms，不是瓶颈 |
| IPC 传 27.4MB 文本 | 568 ms，不是瓶颈 |
| 注解解析 | 0 条（>6 万行自动跳过），不是瓶颈 |
| 独立页（Chromium）挂 41 万行文档 | 建视图 105 ms |
| app 页面 + **全部应用 CSS** + 应用扩展组合 | 建视图 **5 ms** |
| **真实运行环境（WebView2）** | 建视图 **24–30 秒** |
| 空文档挂载 CodeMirror（延迟填充后） | 仍 **29,865 ms** ← 决定性一击 |

**空文档也要 30 秒** ⇒ 与文档大小、扩展、渲染行数、CSS 全都无关；
唯一变量是 **WebView2 里"把大文本交给窗口"这条路径本身**。

### 3. 反向验证：换成原生 textarea 也不行

同一份 26.4MB / 413,598 行文本灌进 `<textarea>`（Chromium 实测）：

```
灌入文本（含全量布局） 4,601 ms
改一个字             4,632 ms   ← 每次编辑都重新布局
滚动                 1 ms
```

结论：**"换成记事本式控件"解决不了问题**（浏览器 textarea 会全量排版；Windows 记事本快是因为
原生控件只格式化视口）。

---

## 三、结论

1. **大文本不许进窗口**：整份文本进 WebView 是卡死的根因，与是否挂编辑器无关。
2. **编辑器不是罪魁**：CodeMirror 在同环境下 5 ms；但它在 WebView2 里被放大上千倍，不能用来承接几十兆文本。
3. **可行通道**：**文本留在后端，窗口只取"当前一页"**（等价于"把外部记事本的能力内置进来"）。

---

## 四、方案：页式 TXT（已实现 v4.5.8）

```
打开大文件
  ├─ 后端：不再整份下发文本（GetFile 大文件分支：text="" + textOmitted）
  └─ 前端：LargeTextView
        ├─ GetFilePage(index, page)      # 每次只取一页（默认 2000 行 ≈ 130KB）
        ├─ 页内原生 textarea 直接编辑    # 记事本手感，毫秒级
        └─ SetFilePage(index, page, text) # 后端把该页拼回全文 → core.setText（归档内存）
                                            → 顶部「未保存修改」+1 → 用户点「保存 PVF」落盘
```

要点：
- 拼接在 **Go 侧**做（几十兆字符串不进 IPC）；写的路径与编辑器保存**完全同一条**（`core.setText`，
  字符串表保护、搜索名同步、未保存计数都自动生效）。
- 切页 / 关标签前**自动提交本页**，不丢改动。
- 大文件不再挂：CodeMirror、注解、语法着色、清单名称标签、补全、跳转关联。

### 关键常量（三处阈值，都要一起看）

| 常量 | 位置 | 值 | 含义 |
| --- | --- | --- | --- |
| `bigFileBytes` | `services/editor.go` | 8 MB | 归档内原始体积超它 → 大文件 |
| `bigTextBytes` | `services/editor.go` | 4 MB | **解码后**文本超它 → 大文件 |
| `bigTextLines` | `services/editor.go` | 100000 | 展开后行数超它 → 大文件 |
| `largeTextLinesPerPage` | `services/large_text.go` | 2000 | 每页行数 |

> ⚠ `list/equipment.lst` 归档内只有 4.13 MB（< 8 MB），是靠**解码后** 27 MB / 41 万行才判为大文件的
> —— 只按归档体积判断会漏。

## 六、踩坑清单

1. **别用"空文档挂载再写入"绕过**：这一招对"挂载慢"有效，但本例挂载本身就是瓶颈（空文档也 30 秒）。
2. **别只看后端耗时**：后端 265 ms，卡在前端；不打卡点就只能猜。
3. **`performance.now()` 的打点在"挂载后统一 push"**：两条打点的时间戳会几乎相同，
   真正有用的信息是**打点里带的毫秒数**，不是时间戳。
4. **对照实验必须同环境**：在独立 Chromium 页里测出来 5 ms 不能证明"环境没问题"——
   真实环境是 **WebView2 + 开着 543MB 归档 + Go 侧 5GB 堆**。
5. **大文件下 `tab.text` 是空串**：任何读 `tab.text` 的功能都要显式拒绝，否则会"拿空串当真内容"
   （已修：list 查重、文件预览；已核对无风险：注册到 lst 走 Go 侧索引）。
6. **异常文本也必须挡**：`abnormal`/空文件等边界同样要先判类型与体积，再决定通道。

## 七、这套架构下"要回哪些功能"的可行性

页式通道已经是"可编辑 + 可保存"，因此绝大多数功能都能以**按页 / 后端代劳**的方式要回来：

| 想恢复的功能 | 做法 | 代价 |
| --- | --- | --- |
| 搜索命中 → 跳到目标页并选中该行 | 后端能按行算页号，前端打开对应页 | 小 |
| 页内查找（下一个/上一个） | textarea 之上自己实现（浏览器原生 Ctrl+F 在 WebView2 里不可靠） | 中 |
| 整篇查找（多命中列表 → 点击跳页） | 后端新增"单文件内查找"，前端结果面板 | 中 |
| list 查重 | 挪到后端对全文查重（前端只显示结果 + 跳页） | 中 |
| 文件预览 / 结构树 | 后端解析整篇，前端按页展示 | 中 |
| 字符串引用插入（`{8=<表::键>}`） | 在 textarea 光标处插入文本 | 小 |
| AI 引入（把内容给 AI） | 后端直接读全文（不经窗口） | 小 |
| **着色 / 注解 / 名称标签 / Ctrl+单击跳转（一揽子）** | **页式 + 每页一个 CodeMirror**：每页仅 130KB，挂载 5–100 ms | 中 |

> 最后一行是"最大的一揽子方案"：它把整份 27MB 的问题还原成"每次只处理 130KB"，
> 因此当年因大文件而被关掉的那些编辑器能力，可以按页全部装回来。

## 九、根因对比分析（2026-09-30 定稿）

### 9.1 台账当年缺的"三段耗时"，实测如下

| 环节 | 实测 | 是不是瓶颈 |
| --- | --- | --- |
| 解码（归档 4.13MB → 文本 27,406,042 字符） | 265 ms | ❌ |
| IPC 传输（27MB 文本） | 568 ms | ❌ |
| 建状态（文档 + 扩展） | 28 ms | ❌ |
| **建视图（`new EditorView`）** | **24,366 ms（空文档也 29,865 ms）** | ✅ 就是它 |
| 首帧 | 31,865 ms | ✅ 连带 |
| 之后 | 停摆 43 s → **每 11 秒一轮** | ✅ |

> 结论：台账 2026-09-28 记的方向（虚拟滚动 + 按可视区取数）是对的，但它猜的"分块解析"不是刀口
> —— 后端本来就快（265 ms）。**真正缺的是"分块把文本交给窗口"，不是"分块解析"。**

### 9.2 卡死的三层机制

| 层 | 机制 | 证据 |
| --- | --- | --- |
| L1 文本落地 | 27MB 字符串跨 IPC 进 WebView，UTF-16 下约 55MB、多份拷贝 + GC 压力 | 传输 568 ms（本身可接受，但它是后面所有成本的前提） |
| L2 **全量排版 / 视口外工作** | 浏览器对文本控件做**全量布局**（textarea 实测 4.6 s/次）；CodeMirror 虽只渲染视口，但内容高度 **7,000,000 px** 的行映射、装饰、选择与查找映射都随文档线性膨胀 | **空文档挂载也要 30 s**；同代码 Chromium 5 ms → WebView2 把这条路径放大上千倍 |
| L3 内存挤压 | Go 堆 5.3 GB + 归档 543 MB + 窗口侧几十兆字符串 → 系统内存吃紧，渲染进程被换页/GC 饿死 | 停摆呈**周期性 11 秒一轮**，只有"资源被反复抢走"能解释循环 |

> ⚠ 诚实标注：L2 的"放大上千倍"与 L3 的占比是**对照实验推断**（拿不到 WebView2 的 profiler），
> 但方向有硬证据：**空文档也 30 秒 ⇒ 与文档大小 / 扩展 / 渲染行数 / CSS 全都无关**。

### 9.3 为什么系统记事本不受影响

原生控件（只格式化视口）+ 本地读文件（无 IPC）+ 不跑 JS / 不建行对象 / 无响应式 + 无内存竞争者。
**这四条在浏览器里一条都抄不到** —— 所以"把外部 TXT 内置"的正确做法不是换控件，
而是**换数据通道**（文本留后端，窗口只取视口）。

### 9.4 五个版本的对比：唯一有效的自变量

| 版本 | 窗口里同时存在的文本量 | 结果 |
| --- | --- | --- |
| 最初：整份 + CodeMirror | 27.4M 字符 | 停摆 43 s + 每 11 s 一轮 |
| v4.5.5：延迟填充（空 CM 再写入） | 空 → 27.4M | 空文档挂载就 29.9 s |
| v4.5.6：整份 + 原生 textarea | 27.4M | 打开 4.6 s、每次编辑 4.6 s |
| v4.5.8：分页 TXT | 130KB（一页） | 秒开 ✅（但翻页） |
| **v4.5.11：连续全文 TXT** | **~20KB（视口几百行）** | **秒开 + 连续滚动 ✅** |

**有效自变量只有一个：窗口里同时存在多少文本。** 文档大小、扩展、CSS、渲染行数、
"是不是 CodeMirror" —— 全部被对照实验排除。

### 9.5 版本史印证

`4.1/4.2 = 大文件与性能专项` → `4.3 = 超大清单限制全部取消（不再只读预览、不需要解锁）`
→ 护栏拆掉后卡死成为日常体验问题 → `4.5.4 ~ 4.5.11` 一路排障。
**今天等于把"只读预览"这道护栏换成了正解。**

### 9.6 一句话经验

> **性能问题先别怀疑算法：先问"数据在哪儿"和"谁在排版"。**
> 这一仗的敌人不是解析（265 ms），而是"把 2740 万字符交给 WebView 去排版"。
> 另一条：**"空文档也慢"这种反直觉现象一旦出现，说明问题在通道，不在数据规模。**

## 十、v4.5.11 升级：连续全文 TXT（替代分页）

| | v4.5.8 分页 | **v4.5.11 连续全文** |
| --- | --- | --- |
| 观感 | 一次一页（2000 行） | **spacer 撑开全文高度，一路滚到底** |
| 取数 | `GetFilePage(index, page)` | **`GetFileLines(index, startLine, count)`（按视口）** |
| 写回 | `SetFilePage(index, page, text)` | **`SetFileLines(index, startLine, lineCount, text)`** |
| 组件 | `LargeTextView.vue`（已弃用） | `src/components/LargeScrollView.vue` |
| 定位 | 无 | 已接 `reveal.line` → 滚动到目标行 |

实现要点（改这一块前必看）：
1. **固定行高**：`ROW_HEIGHT = 20`，textarea 的 `line-height` 必须严格等于它，否则虚拟定位会漂；
2. **不折行**（`wrap="off"`，长行横向滚动）：折行会让行高不固定，虚拟定位失效 —— 这是刻意的取舍；
3. **串行化后端交互**：滚动会连发请求，用 `enqueue` 把 `commit → loadWindow` 串起来；
4. **提交时机**：失焦 / 滚出该段 / 点「保存本段」/ 卸载前；提交只传当前那几百行。
