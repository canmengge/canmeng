## 三、省时间的四条纪律（AI 必守）

1. **先查本表再开文件**，不要一上来全项目搜索（一次广搜能吞掉大量上下文，还常常被截断）。
2. **同一文件不要重复读**：一次用 `offset/limit` 读够，或只读改动附近的一段。
3. **搜索要窄**：给定目录 + 具体词；不要开大段上下文（`-C 3` 之类）。
4. **`本人备份AI不要动\` 只作只读参考源**——改编辑器时不在里面搜、不改、不删；要引用文档时从它复制。

## 五、踩坑经验（实测，别再踩第二次）

> **维护方式**：用户发「保存进度」时，若本轮踩了新坑，就往这里**追加一行**；没踩就不动。

| # | 坑 | 正确做法 |
| --- | --- | --- |
| 1 | `.cmd` 脚本存成 UTF-8（**改现有 `.cmd` 也一样会中招 —— 普通写文件工具会把已有中文写坏**） | 必须 **GBK(936)** 保存，否则 cmd.exe 中文乱码、连中文文件名都解析失败。**改现有 `.cmd` 的安全做法**（2026-10-01 实测）：`$e=[System.Text.Encoding]::GetEncoding(936); $t=[System.IO.File]::ReadAllText($p,$e); [System.IO.File]::WriteAllText($p,$t.Replace($old,$new),$e)` —— **不要**用写文件工具。**验证**：改完 `git diff --numstat` 该文件**只变 1 行**（改出好几行 = 编码被写坏了） |

| 11 | `git push` 到 GitHub 报 `Failed to connect to github.com:443` / `Connection was reset`（`Test-NetConnection github.com -Port 443` 显示 **ping 通但 TCP 不通**，本机无代理） | **推送失败 ≠ 改动丢失**：本地 `commit` 与 `v<版本>` 标签照常完成、随时可回档；`push` 待网络恢复再补。应急可临时 `git -c http.proxy=http://127.0.0.1:<端口> push`（**不要改全局 git 配置**）。**两点补充（2026-10-01 实测）**：① **可能是间歇性的** —— 同机同日 `git push` + `push --tags` **一次成功**（`5706461..1264ec7 main -> main`，5 个标签全推上），**失败别放弃、稍后重试**；② **别把 PowerShell 的 `NativeCommandError` 当成 push 失败** —— git 把进度写到 **stderr**，PowerShell 会渲染成红字报错，**实际常常已成功**；判断成败看 **exit code** 与末行 `<旧>..<新>  main -> main`，或事后 `git log origin/main --oneline -1` 核对。**第三次实测（同日稍晚）：GitHub 真的不可达** —— `git push` 报 `Connection timed out after` **`300058 ms`（≈5 分钟！）**，`git push --tags` 报 `Failed to connect to github.com:443 after 21099 ms`。⇒ **① 之前用户说的"卡住"，真身多半就是这 300 秒连接超时**（不是死锁）；`GIT_TERMINAL_PROMPT=0` **只防"等凭据输入"，防不住连接阶段**，别以为加了它就万事大吉。**② 想要"有界重试"**（不让它一次卡 5 分钟）：把 push 丢进后台作业再加超时 —— `$j=Start-Job { git -C "d:\110AI" push }; if (Wait-Job $j -Timeout 40) { Receive-Job $j } else { Stop-Job $j; Remove-Job $j -Force; 'TIMEOUT 40s' }`。**③ 网络不通时别硬重试**：本地 `commit` + 标签照做，等恢复再补（本行开头口径） |
| 12 | 改完 Go 只让用户"重启工具"，自己没构建 exe | **无效，会白跑一轮**：`启动HMR热更新.cmd` 只是挑 `04-运行环境\` 里**文件时间最新**的 `PVF工坊-开发人员专用*.exe` 来启动，**它只热更新前端、从不重新编译 Go**；"重启"只会把**旧 exe** 再跑一遍（2026-09-29 真实事故：改完 `services\import.go` 未构建，用户测到旧行为、误以为修复无效）。正确三步：① **AI 自己 `go build`** 出带时间戳的新 exe → ② **核验**新 exe 时间晚于源码修改时间、且在 `04-运行环境\` 中最新 → ③ 让用户**先关当前工具**再双击 HMR 脚本（详见 `01-项目开发规则.md` §0「改了 Go 的强制收尾三步」） |

| 14 | 用「写文件」工具改过 `.vue` / `.ts` 后提交，diff 突然多出几百行 | **行尾符被换成 CRLF，把真实改动淹没**：本仓库 `core.autocrlf=false` 且无 `.gitattributes`，索引里主流是 **LF**；工具写文件可能按 CRLF 落盘，于是"只改了 10 行"变成"599 增 / 534 删"（2026-09-29 踩坑：`DevPanel.vue`）。**识别**：`git diff --numstat` 的增删行数远大于实际改动，而 `git diff --ignore-all-space --numstat` 立刻变小 → 就是行尾问题。**修复**：把这些文件按 LF 重写并保持 UTF-8 无 BOM 后再提交；**预防**：改完 `.vue` / `.ts` 提交前扫一眼 `git diff --numstat`，异常先转 LF。**新建文件同样默认 CRLF** —— 2026-09-30 再次踩到（一次新建 4 个文件，全部要先转 LF 才能提交）。排查命令：`git ls-files --eol <路径>`（`i/` 是索引行尾、`w/` 是工作区行尾） |
| 15 | 想让**改 store 也免重启**，给 Pinia store 加 `acceptHMRUpdate`（或改完 store 直接靠 HMR） | **两种做法都会留下半坏状态，store（`frontend\src\stores\*.ts`）改动一律"改完告知用户重启一次"**：① **不注册** → 热更新后页面是「新组件 + 旧 store」，组件调用 store 上新加的方法直接抛 `xxx is not a function`（2026-09-30 实测 `editor.pendingSegmentsOf is not a function`，表现为大文件编辑区空白、像卡死）；② **注册** → Pinia 热替换会**新建一个 store 实例**，而先初始化好的组件仍握着**旧实例** ⇒ 界面看着全在（旧实例里有标签有内容），但「保存」读的是**新实例的空状态** ⇒ **点了没反应、还说"没有待保存的修改"**（2026-09-30 真实事故：v4.5.20 加、v4.5.21 回退）。**正确做法**：改 store 后明确说"需重启工具"；组件调用 store 新增方法要防御（`typeof x === "function"` / 可选链，让降级只丢功能不白屏）；只有**纯组件与服务层**改动才靠 HMR 秒级生效 |
